## Q1 — Three-way merge for markdown templates

### Decision

Use **line-based diff3 three-way merge** (e.g. `node-diff3`'s `diff3Merge`/`mergeDiff3`, or `git merge-file --diff3` if a git dependency is acceptable) with:

- `o` (base) = the template **rendered** at the per-dest `kitCommit` with the recorded placeholder values for this project.
- `a` (ours) = the current project file.
- `b` (theirs) = the new template rendered with the **same recorded placeholder values**.
- Hunk granularity: whole lines, adjacent changed lines coalesced into one conflict region (standard diff3 behavior).
- `{{PLACEHOLDER}}` policy: placeholders are substituted into both `o` and `b` **before** merging, so a line the project filled is never diffed against a `{{KEY}}` token. If the kit introduces *new* `{{KEY}}` tokens that merge cleanly into the file, the sync leaves them in place, marks the dest `needs-fill`, and lists the pending keys in the sync report — never treats them as conflicts. If a hunk containing a token line is genuinely changed on both sides, emit a normal conflict (no token-aware auto-resolution).
- Conflict markers: git-diff3 style, four-part, with descriptive labels:

  ```
  <<<<<<< project
  ...local lines...
  ||||||| kit base <kitCommit-short>
  ...base lines...
  =======
  ...kit lines...
  >>>>>>> kit v<manifest.version>
  ```

  This format is already parseable by `git status`, every editor's merge UI, and cruft users. For markdown it is safe: markers are plain lines, they render as visible text if committed accidentally (not silently wrong), and the `|||||||` base section is what makes resolution tractable in prose.
- After writing, sync scans every merged dest for `<<<<<<<` and for unfilled `{{[A-Z_]+}}` tokens and reports both; a file containing markers is recorded as `unresolved` in state and is never auto-merged again until the marker scan is clean.

### Rationale

- A real base exists: `kitCommit` identifies the exact template bytes, and recorded placeholder values reconstruct the rendered base exactly. With a real base, diff3 is strictly more informative than patch-application: patch application is the degenerate case where a failed hunk becomes a `.rej` file instead of an in-context conflict (cruft's exact failure mode, cruft issue #181: "patch does not apply … Rejected hunk").
- Rendering placeholders into base and theirs collapses "project filled the placeholder" into an ordinary `a`-side change: if the kit didn't touch that line, the project's value survives silently; if the kit did, it's a real semantic conflict that deserves a marker — exactly what you want for e.g. a new `TEST_COMMAND` hint vs. a filled `TEST_COMMAND`.
- Line granularity is the proven unit for git/hg/diff3 and matches markdown structure (prose wraps at line level; headings and lists are lines). Sub-line merging produces unreadable conflict regions in prose.
- Keeping unfilled `{{KEY}}` in merged output (instead of erroring) preserves forward progress and is discoverable — matches the kit's existing convention where new projects get TODO placeholders (README.md:382-383).

### Alternatives rejected

- **Patch-application (cruft-style)**: diff(old-rendered → new-rendered) then apply to the project file. Rejected as the *primary* mechanism because a failed hunk gives `.rej` files with no base context — strictly worse than inline diff3 when the base is available. Retained as a useful mental model (see partial-value).
- **Character/word-level merge (diff-match-patch etc.)**: unreadable conflicts in markdown prose; no ecosystem standard for markers.
- **Merge on raw (unfilled) template as base**: every filled placeholder line becomes a permanent local-vs-base diff, and every kit edit to a token-bearing line produces a spurious conflict. Rejected; retained only as the legacy fallback when placeholder values were never recorded.
- **Special token-aware conflict resolution** (auto-prefer the side that "only substituted tokens"): fragile — cannot distinguish "project filled `{{DEV_PORT}}`" from "project rewrote the whole line" without the rendered base; once the rendered base exists the distinction is unnecessary.
- **HTML-comment conflict markers** (`<!-- CONFLICT -->`): not recognized by any merge tooling; invisible in rendered markdown (silent bad state).

## Q2 — Dotfile-manager prior art

### What each tool actually does

| Tool | How it detects "upstream vs local changed" | Defaults per class |
|---|---|---|
| **chezmoi** | Source state (git repo of templates) vs. target (live file) vs. destination state recorded in chezmoi's internal state DB — it remembers what it last wrote, so "target modified since last apply" is detectable (chezmoi FAQ; issue #4180 shows `status` columns = "diff vs last apply" and "diff vs source"). | **upstream-only** → `chezmoi apply` updates target (fast-forward). **local-only** → on `apply`, prompt overwrite/diff/skip (never silently discards). **both** → `chezmoi merge` opens an external 3-way tool (vimdiff default) on destination/source/target — never auto-merges, never writes conflict markers. **neither** → no-op. |
| **GNU stow** | No upstream concept at all — symlink-farm model. "Ownership" is the only notion: a path is a conflict iff it exists and is not a symlink stow owns (`Stow.pm` default options; man stow.8). | Every unexpected existing file → **abort the whole operation** ("All operations aborted"). Escape hatches are opt-in flags: `--adopt` (pull foreign file into package), `--defer`/`--override` regexes for package-vs-package collisions. Conservatism taken to its limit. |
| **cruft** | `.cruft.json` records template URL + **git commit** + the cookiecutter context (variables) + a `skip` list. Update regenerates the project at the recorded commit and at HEAD in temp dirs, diffs *those two renderings*, and applies the delta to the project via `git apply --3way`, falling back to `git apply` then `patch` → `.rej` files (cruft docs; issue #181). `cruft diff`/`cruft check` expose drift. | **upstream-only** → applied. **local-only** → local delta is invisible to the patch unless it overlaps → applied cleanly or conflicts. **both** → `.rej` reject files; never silently resolved. **skip** → `.cruft.json` `skip` list = per-path permanent opt-out. |

### Decision — defaults this kit should adopt

Adopt **cruft's recorded-base + rendered-diff model upgraded to true diff3 output**, with **chezmoi's conservatism on the conflict side** and **stow's ownership test as the fast path**:

| Class (per managed dest) | Detection | Default action |
|---|---|---|
| kit changed, project didn't (`sha256(local) == baseHash`, where `baseHash = sha256(rendered base at per-dest kitCommit)`, AND base != new rendered) | hash compare | **Fast-forward**: write new rendered content. |
| project changed, kit didn't (`local != baseHash` AND base == new) | hash compare | **Keep local**: report as "locally modified, kit unchanged". |
| both changed | diff3 | **Merge**; auto-apply clean regions, write git-diff3 conflict markers for conflicting regions, mark `unresolved`. Never discard either side silently (chezmoi principle). |
| neither changed | hash compare | **No-op**. |
| dest in `overrides.skip` | registry | **Skip always** (cruft `skip` equivalent). |
| dest deleted by project | file absent + state entry present | Leave deleted + report; recreate only with `--restore-deleted` (project intent wins). |
| dest exists but was never kit-managed (no state entry) | no base | **Skip always** (current scaffold behavior preserved for foreign files). |

**Critical state invariant**: the fast-forward test compares `local` to the *rendered kit base* (`baseHash`), never to the content last written (`writtenHash`). After a merge the written file embeds local edits, so `writtenHash != baseHash`; treating `writtenHash` as "untouched" would fast-forward over those edits on the next sync. `writtenHash` is recorded only to detect edits-since-sync for reporting — it is never the merge classifier.

Two-sync walkthrough (the regression the schema must survive):

- **Sync 1** at kitCommit `c1`: base `R0` = rendered template at the file's previous `c0`; local `L1` carries project edits → diff3(`R0`,`L1`,`R1`) = `M1`, written. State: `kitCommit=c1`, `baseHash=sha256(R1)`, `writtenHash=sha256(M1)`.
- **Sync 2** at `c2` (new render `R2`), project untouched: `local == M1 != baseHash(R1)` → *not* fast-forward → diff3(`R1`,`M1`,`R2`) replays the local delta onto `R2` → `M2`, edits preserved. If instead `local == baseHash` (last write was a clean render) → fast-forward to `R2`. If the project edited `M1`→`L2` → diff3(`R1`,`L2`,`R2`) merges the new edits too.

### Rationale

- cruft is the closest prior art — template registry + rendered diff + recorded commit — and its real-world failure mode (rejected patches with no base context, issue #181) is precisely what diff3 fixes. We take cruft's *model* and fix its *output*.
- chezmoi demonstrates the correct conservatism: its "record what you last wrote" state DB is exactly our per-dest `hash` field, and it never auto-merges without a human.
- stow contributes the "ownership" test — `local == recorded base` is our equivalent of "a symlink stow owns" — and the skip-always default for foreign files.

### Alternatives rejected

- **chezmoi's external merge tool / prompt-on-everything**: `onboard.mjs sync` must run non-interactively (factory automation); interactive merge is a manual follow-up, not a default.
- **stow's abort-on-any-conflict**: too coarse for content files — one local edit would freeze all kit updates.
- **cruft's `.rej` output**: superseded by diff3 markers (Q1).

## Q3 — Skills CLI semantics

### Findings (verified against `vercel-labs/skills` source + docs)

1. `npx skills update [skills...]` reads `~/.agents/.skill-lock.json`, filters entries by **exact skill name** — `matchesSkillFilter` does `filter.some(f => f.toLowerCase() === name.toLowerCase())` (`src/update.ts`). Positional filters are skill *names*, not `owner/repo@skill`.
   - **Consequence: `npx skills update obra/superpowers@brainstorming -g -y` (scaffold.sh:217) matches nothing and silently no-ops.** The kit's current `--update-skills` path is very likely broken. Fix in sync engine: `npx skills update <name> -g -y` or bare `npx skills update -g -y`.
2. Update = check + reinstall: compares the lock entry's `skillFolderHash` (GitHub git-tree SHA of the skill folder) against the latest via the update API / Trees API, then re-runs `npx skills add <tree-url> -g -y`, preserving agent links and updating `updatedAt` (commands/update docs; `update.ts:updateGlobalSkills`).
3. **Version pinning: refs only, and only on the install side.** Skills have no semver. `skills add` accepts `owner/repo#<ref>` / `.../tree/<ref>` sources and the lock entry records `ref`; `buildUpdateInstallSource`→`appendFolderAndRef` in `update-source.ts` re-appends `entry.ref` when building the reinstall source, so `skills update` *reinstalls at the recorded ref* rather than the default branch. The update *check* groups lock entries by `(source, ref)` and fetches the repo tree **at the recorded ref** (`update.ts` — key `source\nref`, `fetchRepoTree(source, firstEntry.ref)`), so "update available" on a ref pin means that ref's upstream tree moved (branch advanced, tag repointed) — a real signal, not noise. For immutable commit refs the tree cannot move; a mismatch there indicates drift worth flagging. There is **no content-hash pin**: a `skillFolderHash` cannot be expressed to the CLI as an install target.
4. Update-trackable entries require `skillFolderHash` + `skillPath` in the lock; local-path, non-GitHub git, and well-known sources are skipped (update.ts `getSkipReason`). Upstream-deleted skills are **not** removed in `-y`/non-interactive mode (`promptDeletions` — good for automation).
5. Scope: `-g` updates only global skills; with `-y` and no scope flags the CLI auto-detects project vs global.

### Decision

Sync implements **ensure → reconcile-pins → update → verify**:

1. **Ensure**: if `~/.agents/skills/<name>/SKILL.md` absent and manifest `required` → `npx skills add <source>@<skill> -g -y` (unchanged).
2. **Reconcile pins**: for each `ref:` pin, compare `lock.ref` to the pin. If they differ — e.g. the pin was added or changed *after* the skill was installed on another ref — `skills update` will only preserve the *existing* lock ref; it cannot move a skill onto a new pin. Explicitly reinstall the single skill at the pin first: `npx skills add <source>#<pin-ref> --skill <skill> -g -y`. The `--skill` selector is mandatory — bare `add <source>#<ref> -y` discovers and installs **every** skill in that repository.
3. **Update**: `npx skills update <name> -g -y` (name only — never `source@skill`). Excluded: `hash:`-pinned names (not CLI-expressible) and `ref:` pins to immutable commit SHAs (a commit's tree cannot advance — update is a no-op). `ref:` pins to branches/tags may update; the CLI preserves the recorded ref and upstream movement on that ref is the point of a movable pin.
4. **Verify**: re-check `~/.agents/skills/<name>/SKILL.md` exists AND read the `~/.agents/.skill-lock.json` entry → record `skillFolderHash` and `ref` into state. For `ref:` pins additionally require `lock.ref == <ref>` after reconcile+update; a post-reconcile mismatch = pin not applied → report failure, do not mark synced. If SKILL.md missing → report failure, do not mark synced.
5. **Pins**: `overrides.pins["<skill>"]` takes two typed forms with distinct validation:
   - `"ref:<branch|tag|commit>"` — CLI-native: realized via `npx skills add <source>#<ref> --skill <skill> -g -y` (or a `/tree/<ref>/<path>` URL, which is already skill-scoped); the lock records `ref`, `update` preserves it. Movable refs (branch/tag) are updated like normal; immutable commit refs skip update. Verify `lock.ref == <ref>`. An "update available" check result on a ref pin is *real* (the check diffs the ref's own tree) — report it as upstream-drift-on-pin, never ignore it.
   - `"hash:<skillFolderHash>"` — content pin, not expressible to the CLI (a folder hash is not an installable ref). Kit-side only: never pass to `skills update`; verify `entry.skillFolderHash == <hash>` and flag drift for manual repin. Verify-only unless the pin also records the commit that produced the hash (then `ref:<commit>` is the better form).

### Rationale

- Aligns with actual CLI behavior rather than assumed behavior; fixes the silent no-op in the current script.
- `skillFolderHash` gives a content-level verification signal — the kit's verify step is the same check the CLI itself uses.
- Kit-side `hash:` pins are honest about the CLI boundary: semver/content pinning doesn't exist upstream; `ref:` pins delegate to the CLI's own `ref` mechanism — but only after reconciliation, since `update` preserves the *existing* lock ref and never moves a skill onto a new pin.

### Alternatives rejected

- **`npx skills update <source>@<skill>`** — silently matches nothing (finding 1).
- **Rely on CLI lock file as sole state** — lock file is global and shared across projects; per-project `pins`/`skip` need kit-side records.
- **`experimental_install` / project `skills-lock.json`** — experimental, and the kit installs globally (`-g`) today; project-scoped skills are a separate policy decision.
- **Auto-remove upstream-deleted skills** — the CLI correctly refuses in `-y` mode; keep that. Report only.
- **Assume `skills update` applies a pin** — it preserves the *recorded* ref; a pin added or changed after install requires an explicit `skills add <source>#<ref> --skill <skill>` reconcile first (the `--skill` selector is required — bare `add` with `-y` installs every skill in the repo).

## Q4 — Managed-key JSON merge policy (mcpServers, hooks)

### Decision

Move `mcpServers` and `hooks` from skip-always to **managed-key follow-the-kit**, where "customized" is detected per *entry* (per server name / per hook event), not per file:

- State records, per agent config path, per managed key, a **base hash**: `sha256` of the canonical JSON serialization of the manifest entry as installed (canonical = sorted keys, no insignificant whitespace). e.g. `configBases[".devin/hooks.v1.json"]["PreToolUse"] = <hash>`.
- On sync, for each manifest entry targeting that config:
  - installed entry canonical-hash `==` recorded base hash → **not customized** → replace with the new manifest entry.
  - installed != base → **customized** → keep local, report, write sidecar (below). Never inline-merge a customized entry.
  - entry absent locally + a `configBases` base exists for the key → **project deleted a managed entry** → leave absent + report; restore only via `--restore-deleted` (same rule as Q2's deleted dest — deleting an MCP server or hook event is as intentional as deleting a managed file).
  - entry absent locally + no recorded base → add (indistinguishable from never-installed; matches the scaffold's existing add-missing behavior).
- **Legacy entries (no recorded base)**: one-time backfill — reconstruct the manifest at `state.kitCommit` (`git show <kitCommit>:onboard.manifest.json`) and compare the installed entry to the kitCommit entry:
  - equal → record base; entry becomes managed (normal rules apply this same run);
  - different → mark entry customized, record base as `null`, stays skip-always;
  - `kitCommit` unknown/unfetchable → stays skip-always unless the user runs `sync --adopt-managed`.
- **Conflict format**: never write markers inside JSON (invalidates the file for every consumer — agent config parsers will hard-fail). Write a sidecar `<configPath>.kit-incoming.json` — a single JSON object **keyed by managed key** (MCP server name or hook event) aggregating all outstanding proposed entries for that config path; upserted each run so later conflicts can't clobber earlier proposals, deleted when emptied — plus an entry in the sync report. `--json-theirs` / `--json-ours` per-key resolution flags are a later CLI nicety.

### Rationale

- Risk of updating never-customized entries is **low and bounded**: the kit owns these entries end-to-end (e.g. `context-mode hook …` strings in `onboard.manifest.json:110-143`); if the project never touched them, following the kit is the desired behavior — it's how `.hermes/hooks.json` picks up a fixed hook command.
- Hash-on-canonical-serialization is cruft's `.cruft.json` / chezmoi's state-DB trick at entry granularity; it detects *semantic* customization while ignoring reformatting.
- Backfill-by-kitCommit-comparison gives legacy projects the upgrade path without making git archaeology steady-state.
- Keeping genuinely-customized entries skip-always preserves invariant #1 (non-destructive) — the riskier direction (auto-overwrite customized config) is what breaks trust.

### Alternatives rejected

- **Inline conflict markers / merged JSON with `<<<<<<<`** — produces invalid JSON; every agent config reader crashes. Hard reject.
- **Sub-field 3-way JSON merge** (auto-merge inside a customized entry) — semantic merging of command strings/args arrays is guesswork; high blast-radius for agent configs. Report + sidecar is honest.
- **File-level granularity** (whole `hooks.json` managed or not) — too coarse; a project customizing `PostToolUse` shouldn't lose `PreToolUse` fixes.
- **Detect customization by comparing to *current* manifest only** — false positives whenever the kit itself changed the entry since install.
- **mtime/size heuristics** — unreliable (editors touch, checkouts rewrite); hash only.

## Q5 — Registry/state schema v1 review

Proposed (card): registry = `{name, path, agents, onboardedAt, lastSyncAt, overrides{skip,pins}}`; state = `{kitCommit, manifestHash, per-dest{hash, source, syncedAt}}`.

### Decision

Adopt the proposed schema as the skeleton and add **6 fields required for merge safety**:

| # | Missing field | Why it's needed |
|---|---|---|
| 1 | **`schemaVersion`** on both files | Non-negotiable for any file read across kit versions. |
| 2 | **per-dest `kitCommit`** (or `baseTemplateHash`) | Global `kitCommit` assumes all dests synced atomically; a file synced 3 releases ago has a different base than one synced yesterday. Merge needs the per-dest base. |
| 3 | **`placeholders` values map** (per project, in state) | The single most important omission — without recorded values the rendered base (Q1/Q2 model) cannot be reconstructed and merges degrade to raw-template base with spurious conflicts. Record `{"PROJECT_NAME": "...", ...}` at fill time. |
| 4 | **`configBases`** (state): per config-path, per managed-key entry hashes | Q4's entire managed-key policy depends on it. |
| 5 | **`unresolved` / `lastSyncResult`** (state) | Files containing conflict markers or pending `{{KEY}}` fills must be re-detectable; sync should refuse to merge over an unresolved file (or require `--force`). |
| 6 | **`skills` section** (state): per-skill `{source, skill, skillFolderHash, pinnedRef?, syncedAt}` | Needed for Q3 pins + verify step; the CLI lock is global and can't express per-project pins. |

### Rationale

- Every added field is load-bearing for a decision above: `placeholders`+per-dest `kitCommit` make the Q1 rendered base reconstructable; `configBases` makes Q4's customization detection possible; `unresolved` makes Q1's never-re-merge-a-conflicted-file rule enforceable; `skills` makes Q3's kit-side pins expressible.
- Clarifications on existing fields:
  - `per-dest.hash` must be **split into two fields** — this is the merge-safety crux:
    - `baseHash` = sha256 of the *rendered kit base* at `files[dest].kitCommit` — the merge/fast-forward comparator (`sha256(local) == baseHash` → untouched by project).
    - `writtenHash` = sha256 of the content actually written at last sync — diverges from `baseHash` exactly when a merge embedded local edits; used only for edits-since-sync detection/reporting, **never** as the fast-forward test (using it would overwrite merged local edits on the next sync — see the two-sync walkthrough in Q2).
    - `templateHash` = sha256 of the raw `.tmpl`, kept for provenance — the card's "sha256 of template content recorded pre-placeholder-fill" is this field, not the merge guard.
  - registry `path`: normalize to absolute canonical path; store kit repo URL/`kitRef` if the engine may run from a different clone.
  - `overrides.skip` should accept both dest paths and managed config keys (e.g. `".devin/config.json:mcpServers.semble"`) — same opt-out mechanism for Q4.
  - `onboardedAt`/`lastSyncAt`: ISO-8601 UTC.

### Alternatives rejected

- **Per-entry content snapshots in state** — rendered base is reconstructable from `kitCommit` + recorded placeholder values; storing full snapshots duplicates what git already stores and invites drift between snapshot and reality. Revisit only if the kit ever ships without git history.
- **`size`/`mtime` merge guards** — unreliable (editors touch files, checkouts rewrite mtimes); sha256 compare is the correct guard. A `sizeBytes` fast-path is optional cosmetics, not safety.
- **Merging registry and state into one file** — registry answers "which projects" (kit-side, append-friendly), state answers "how to merge this project" (project-side, per-dest bookkeeping); different lifetimes and writers.
- **Storing rendered base text instead of kitCommit** — bloat, no provenance, and loses the ability to backfill via `git show`.

## Complexity & limitations

- **Rendered-base reconstruction requires recorded placeholder values** — a new write-path during onboard (fill → record values) that doesn't exist today. Legacy projects without values fall back to raw-template base (more conflicts on first sync, self-healing after).
- **diff3 on prose**: adjacent-line edits by both sides still produce noisy conflicts; acceptable (same as git).
- **JSON canonicalization** must be specified (sorted keys, `JSON.stringify` of parsed object, UTF-8, NFC) or hash compare false-positives on formatting.
- **Skills CLI is a moving target** (version churn: e.g. the 1.5.16 Claude-Code link fix per NVIDIA docs); the verify step must not assume lock-file schema — probe `SKILL.md` presence as the primary signal, `skillFolderHash` as secondary.
- **kitCommit resolution** requires the kit clone to retain history (`git show <commit>:…`); shallow clones need a fallback to manifestHash-only mode (no backfill → legacy entries stay skip-always).
- **Deletion semantics** (project deletes a managed file) need the flag decision in Q2's table — easy to get wrong in both directions.

## Partial-value analysis

- **cruft** (`cruft/_commands/diff.py`, `cruft/_commands/update.py`): the temp-dir double-render + recorded-commit + `skip` list is the reference architecture — mine it when building `sync`. Re-review if we ever need patch-export instead of in-place merge.
- **chezmoi state DB** (`chezmoi status` two-column semantics): model for a future `sync --status` distinguishing "kit drifted" vs "project drifted".
- **node-diff3** (`bhousel/node-diff3`): the actual library to depend on — `diff3Merge` returns structured ok/conflict blocks (scriptable) and `mergeDiff3` emits labeled markers. No external diffutils dependency.
- **skills CLI `update.ts`**: `getSkipReason`/`matchesSkillFilter` are the contract for our skills step; re-read before implementing.
- **stow `--adopt`**: the right UX precedent for `sync --adopt-managed` (bring a foreign file under management).

## Recommendation

**adopt-component** — adopt the merged policy set (diff3 + rendered base + managed-key hashing + name-based skills update), assembled from cruft's architecture, chezmoi's conservatism, and stow's ownership test; reject every component's literal mechanism in favor of the diff3/hashing upgrades identified above. Against the gate: every decision is implementer-actionable and preserves all kit invariants.
